# CLAUDE.md

Personalised Offer Engine for J-PAL Punjab Jobs AI Bootcamp, Hackathon 2.
Decides which offer each (synthetic) e-commerce customer should get and delivers it through Telegram bots.
Rules set hard limits; a Groq LLM picks and personalises offers inside those limits; a validator re-checks
every AI choice before anything is sent.

## Project Safety Rules
- Never read, print or commit `.env`. Use `.env.example` to learn which variables exist.
- Bot tokens and API keys live only in environment variables (local `.env`, Render env settings).
- Git: commit small working steps freely in this repo. Do not force-push or rewrite pushed history.
- All customer data is synthetic and generated by `app/data/generator.py`. Never import real customer data.
- Groq is a free-tier key: keep `LLM_ENABLED=false` by default; simulations and tests must never call Groq.

## Architecture
- `app/main.py` — FastAPI app (health checks; later Telegram webhooks + admin dashboard). One Render web service.
- `app/config.py` — settings from env/.env. `postgresql://` URLs are rewritten to the psycopg v3 driver.
- `app/db/` — SQLAlchemy models, session, Alembic migrations (`alembic upgrade head`).
- `app/tenants/registry.py` — multi-tenant registry. Each `tenants/<slug>/` folder = one store + one bot
  (`tenant.yaml`, later `rules.yaml`, `catalog.yaml`). `_template/` is copied to add a bot. Every business
  table carries `tenant_id`.
- `app/data/` — synthetic data: `calendar.py` (Indian sale/festival calendar), `generator.py` (hidden personas →
  daily demand → orders, carts, browsing, points), `loader.py` (replaces one tenant's rows, shifts ids),
  `summary.py` (realism report). `customers.true_segment` and `customers.price_sensitivity` are hidden generator
  traits for evaluation only — the offer engine must never read them. Seed with
  `python scripts/seed.py --tenant shopkart` (~2.5 min to Neon).
- `app/features/` — `customer.py` computes observed features + scores (churn_risk, buy_anyway_prob,
  deal_affinity, expected_value_90d) via portable SQL aggregates and a FIFO points replay; `segments.py` assigns
  segments from `tenants/<slug>/segments.yaml` (first match wins, plain-language reason); `store.py` saves the
  `customer_features` snapshot. Rebuild with `python scripts/build_features.py --tenant shopkart` (~10 s);
  it also prints agreement with the hidden personas (~50%: early churn is genuinely invisible in behaviour).
- `app/features/conditions.py` — the single `<measure>_min/_max` condition grammar shared by segments.yaml and
  rules.yaml audiences.
- `app/rules/` — `schema.py` (rules.yaml model + `check_rules`: load-time business checks such as discount cap <=
  category margin, flat-off % <= cap, known segments/categories), `engine.py` (pure `evaluate()` → Decision with a
  ranked shortlist of Candidates and a plain-language reason for every blocked offer), `policy.py`
  (`load_policy(tenant_dir)` bundles rules + catalog margins + segments). Preview with
  `python scripts/preview_offers.py --tenant shopkart [--customer 17] [--at "2026-10-22 23:00"]`.
  Budget counts worst-case liability of offers sent today. Quiet hours set `send_after`, never block.
- `app/offers/service.py` — links chats to personas, runs features → engine (real offer history + today's
  budget) → template message → records an `offer_decisions` row for every request (incl. no_offer + reason).
  On-demand requests re-show a live offer and ignore quiet hours (user asked).
- `app/delivery/templates.py` — HTML texts. Offer message = intro (AI-writable later) + fixed offer box built
  from the rule-checked Candidate (headline, terms, coupon) so the AI can never change what is offered.
- `app/bot/` — `handlers.py` (/start persona picker, /offers, /profile, /switch, /stop, /resume, /help, Claim /
  Not now / Stop buttons), `runner.py` (one Application per tenant with a token; webhook when PUBLIC_BASE_URL is
  set, else polling). `POST /tg/{slug}/{secret}` checks path secret + Telegram secret header.
- `app/agent/` — `groq_client.py` (`groq_json`: only calls Groq when LLM_ENABLED + key + per-minute and per-day
  caps allow; daily count comes from the `llm_calls` table; any failure → None), `chooser.py` (prompt with
  customer facts as JSON data + top-4 shortlist; model returns offer_key/title/body/reason; per-day cache;
  falls back to the rules' top pick + template and records why), `validator.py` (offer_key must be in the
  shortlist; intro may not contain numbers, money, %, number words, timing claims, extra promises, links, HTML,
  injection echoes, type-mismatched "free"/"points", or other categories). Default model `openai/gpt-oss-120b`
  (reasoning_effort low). Try one customer: `python scripts/try_agent.py --tenant shopkart --customer 17 [--llm]`.
- `app/measurement/` — `holdout.py` (stable hash, `holdout_pct` from rules.yaml; applies to proactive triggers
  only, never to on-demand), `outcomes.py` (simulated world response; MAY use hidden persona/price sensitivity
  because it plays reality, not the engine), `metrics.py` (sent vs matched holdout: uplift ± 95% CI, extra
  profit, Rs returned per Rs of discount, by offer and segment; plus real Telegram stats).
- `app/offers/campaign.py` — batch simulated campaign: budget goes to highest expected-profit offers first
  (fallback to a cheaper shortlisted offer that fits); holdout matched to the funded slice via the day's
  expected-profit cutoff; holdout decisions are "virtual sends" for later days' gaps/caps; budget-stopped
  customers are counted, not stored. `simulated=True` decisions never affect live limits/budget; linked real
  chats are excluded. `python scripts/simulate_campaign.py --tenant shopkart [--days 7] [--budget N] [--reset]`.
- `app/triggers/events.py` — live events (`cart_abandoned`, `points_expiring`, `birthday`) mutate data, refresh
  that customer's features and run the pipeline with trigger `event:<kind>`; pushes to linked chats; quiet hours
  → `deferred`, sent by the runner's 60s dispatch loop. `scripts/live_trigger.py event|campaign ...`.
- `app/rules/policy.py` — `current_policy(slug, dir)`: rules saved from the dashboard (`rules_versions` table,
  newest wins over rules.yaml) are picked up by every process within ~10 s; `save_rules` validates first.
  `BotContext.policy` is a live property. Scripts use `current_policy` too.
- `app/dashboard/` — admin UI at `/admin` (FastAPI + Jinja + Chart.js, tokens/palette from the dataviz skill):
  Overview, Results (uplift vs holdout with CI bars), Segments, Decisions log, Customer page ("what would they
  get now" + blocked reasons + history), Rules editor (form → validated → saved version + history; reset to
  rules.yaml), Actions (simulate campaign, live campaign, fire event). HTTP Basic auth (`ADMIN_USER` /
  `ADMIN_PASSWORD`; refuses `change-me` when PUBLIC_BASE_URL is set) + same-origin check on every POST.
  Static links carry `?v=<mtime>` for cache busting.
- Decision pipeline: features → rules engine shortlist → holdout (proactive only) → AI chooser → validator →
  deliver/push → log (+ simulated outcome for simulations).

## Commands
```
pip install -r requirements.txt
alembic upgrade head                 # create/upgrade tables in DATABASE_URL (Neon)
python scripts/run_bot.py            # run all tenant bots locally (polling)
uvicorn app.main:app --reload        # web app + dashboard at /admin (starts bots by webhook only if PUBLIC_BASE_URL is set)
pytest                               # tests use a throwaway SQLite DB, never Neon, Telegram or Groq
```

### Stage 8 backlog: offer tuning (after measurement, so changes are judged on uplift/redemption data)
- Make offers more attractive where margin allows. User feedback: "₹100 off" for a new customer's second order
  feels weak — e.g. bigger flat amount, % off with a cap, or free delivery + discount combo, while staying inside
  the 10% store-wide cap (raise min order, or target a higher-cap category).
- Review every offer's value vs. its expected_net in `scripts/preview_offers.py`; tune values, min orders,
  validity windows and priorities in `tenants/shopkart/rules.yaml`.
- Consider tiered values by customer value (e.g. bigger win-back for formerly high spenders).
- Re-check message wording/appeal of templates once the AI intro (Stage 6) is in.
- Use `scripts/simulate_campaign.py` results: "Points expiring" shows no clear uplift (-2% ± 23%) and "Loyalty
  bonus" to loyal high-value customers returns < Rs 1 per Rs 1 — rethink or retarget them.
- Calibrate the simulated response model (`app/measurement/outcomes.py`): uplifts like +32 pts for cart comeback
  look generous vs. real-world benchmarks (typically a few points); lower `offer_strength`/`RELEVANCE`.

## Conventions
- Python 3.11, type hints, pydantic for config/rule schemas.
- Keep code portable between Postgres (prod) and SQLite (tests).
- Rules must stay readable by a marketing team: every rule in `rules.yaml` has a plain-language `description`.
